# 11. Синхронизация хранилищ и сквозное шифрование (P5)

**Цель:** хранилище заметок синхронизируется между устройствами через сервер, который видит только шифротекст.
Новые устройства подтверждаются с доверенных, есть ключ восстановления, у каждого устройства своя политика
синхронизации. Это самый ответственный этап: ошибка здесь — потеря данных пользователя.

Связь с решениями: 2.6, 5.2, 5.4, раздел 7 (P5).

## Что изучить

1. Основы прикладной криптографии — **сначала теория, потом код**:
   - симметричное шифрование с аутентификацией (AEAD): XChaCha20-Poly1305 или AES-GCM; что такое nonce и почему
     его нельзя повторять;
   - асимметричное шифрование и обмен ключами (X25519), «запечатанные» сообщения (sealed box);
   - выработка ключей: HKDF; из пароля — Argon2id;
   - обёртывание ключей (key wrapping): ключ хранилища, зашифрованный ключом устройства.
2. Библиотека libsodium — простой и безопасный API: <https://doc.libsodium.org>. В JS — `libsodium-wrappers`.
   Правило: **не изобретай свои схемы и примитивы**, только готовые конструкции библиотеки.
3. Как устроены похожие системы: whitepaper Apple Platform Security (раздел Advanced Data Protection), описание
   протоколов 1Password или Bitwarden. Читай ради схемы ключей, не ради деталей.
4. Трёхстороннее слияние текста: `diff3` (пакет `node-diff3`) и/или `diff-match-patch` (Google).
5. Хранилище объектов: MinIO в docker-compose (S3-совместимое), presigned URL.

## Шаги

### А. Криптография (`packages/crypto`)

1. Ключи устройства: пара X25519 + ключ подписи; приватные ключи — в `KeyStore` (Keychain/Credential Manager/
   Keystore через Tauri; неизвлекаемые ключи в вебе).
2. Ключ хранилища (случайный симметричный ключ). Для каждого доверенного устройства — его копия, зашифрованная
   публичным ключом устройства. Копии лежат на сервере.
3. Ключ восстановления: показывается один раз при включении синхронизации (слова или код), из него выводится ключ,
   которым шифруется ещё одна копия ключа хранилища.
4. Шифрование файла: AEAD, случайный nonce, в связанных данных (AD) — ID хранилища и ID файла, чтобы шифротекст
   нельзя было подменить на другой файл.
5. Тесты: шифрование/расшифровка, подмена шифротекста или AD → ошибка, потеря ключа → данные не читаются.
6. Попроси агента сделать **ревью уровня 3** всей криптографии перед тем, как идти дальше.

### Б. Протокол синхронизации

7. Модель на сервере (Go): `vault`, `vault_file_version { fileId, version, parentVersion, deviceId, blobKey,
   deleted }`, копии ключей хранилища на устройства. Сервер не видит ни путей, ни содержимого: путь файла тоже
   внутри шифротекста.
8. Стабильный ID заметки (открытый вопрос из решений): выбери вариант (frontmatter, индекс в `.flippo/` или оба),
   опиши его в `ARCHITECTURE_DECISIONS.md` и обоснуй.
9. Клиент: для каждого файла храни последнюю синхронизированную версию (базу для слияния). Отправка: новые версии
   с указанием родителя. Получение: если родитель совпадает с локальной базой — применить; иначе трёхстороннее
   слияние; не сливается — сохранить обе версии и пометить конфликт.
10. Правила конфликтов из 5.2: переименование + правка, удаление + правка (правка не теряется).
11. Хранение блобов: Go выдаёт presigned URL на MinIO/S3; клиент загружает шифротекст напрямую.
12. Адаптер хранения как плагин: интерфейс `StorageAdapter` (список версий, загрузить, скачать). Первая
    реализация — Flippo Sync; вторая для проверки абстракции — «папка на диске» (имитация Dropbox).

### В. Устройства и политика

13. Подтверждение нового устройства через механизм из этапа 08 (QR или запрос «Разрешить?»): старое устройство
    шифрует ключ хранилища для нового.
14. Экран устройств: список, отзыв доверия (после отзыва — смена ключа хранилища для новых версий).
15. Политика синхронизации на устройство: какие хранилища, режим авто / по запросу / по событиям.
16. Статусы в UI: «сохранено на устройстве», «синхронизировано», «конфликт», «ошибка».

### Г. P5: проверка

17. Автотесты протокола с двумя-тремя имитированными клиентами и «плохой сетью» (обрывы, повторы, порядок):
    все сценарии из 5.2 и: долгий офлайн, одновременное создание файла с одним путём, отзыв устройства.
18. Ручная проверка на ПК + телефоне. Итоги — в `roadmap/results/p5.md`.

## Готово, когда

- [ ] Ни в одном сценарии теста данные не теряются; конфликт всегда виден пользователю.
- [ ] На сервере в базе и S3 нет открытого текста заметок и путей (проверь глазами и тестом).
- [ ] Новое устройство получает доступ только после подтверждения или ключа восстановления.
- [ ] Ревью криптографии проведено, замечания закрыты.
- [ ] Ты можешь нарисовать схему ключей и объяснить, что произойдёт при потере каждого из них.

## Ловушки

- Повтор nonce с тем же ключом ломает AEAD. Используй XChaCha20 (длинный случайный nonce) или счётчик.
- Не логируй ключи, расшифрованный текст и пути файлов ни на сервере, ни на клиенте.
- Синхронизация не равна резервной копии: удаление тоже синхронизируется. Корзина с хранением удалённого N дней
  обязательна.
