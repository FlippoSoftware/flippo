# 06. Доменный слой и индексатор хранилища

**Цель:** чистый TypeScript-пакет с моделью Flippo и индексатор, который превращает папку `.md` в данные для
поиска, ссылок и обратных ссылок. Отсюда начинается основной код (не прототип).

Связь с решениями: 5.1 (модель данных), 6.1 (модули `domain`, `platform-contracts`).

## Что изучить

- Проектирование доменной модели: агрегаты, инварианты, команды. В репозитории есть навык
  `.claude/skills/domain-modeling` — прочитай его как статью.
- UUIDv7: <https://www.rfc-editor.org/rfc/rfc9562> (раздел про v7) — почему ID с временем удобны для сортировки.
- Vitest: <https://vitest.dev/guide/>.
- Синтаксическое дерево `@lezer/markdown` (уже знакомо по P3) — тот же парсер используется в индексаторе.

## Шаги

0. **Полная модель данных на бумаге.** Нарисуй диаграмму всех сущностей — как схема старого проекта, но по
   разделу 5.1 решений: сущности, поля, связи, где хранится (сервер / устройство / оба), кто может читать
   (сервер или только клиент — из-за шифрования). Положи её в `roadmap/results/data-model.png` (или `.md`) и
   обнови раздел 5.1 в решениях. Попроси агента сделать ревью уровня 3. Это проект, а не код: таблицы по нему
   создаются миграциями на этапах 08–12.
1. `packages/domain/`: типы `NoteId`, `CardId`, `SetId` (брендированные строки), `Note`, `Block`, `Link`, `Card`,
   `Set`, `Folder`, `ReviewEvent`. Генерация ID на устройстве.
2. Инварианты как функции с тестами: «карточка принадлежит одному набору», «копия карточки получает новый ID и
   ссылку на источник», «порядок карточек без дублей».
3. Команды домена (`createCard`, `moveCard`, `copyCardToSet`, `linkNoteToCard`…): чистые функции
   `(состояние, команда) → изменения`. Именно их позже будут вызывать UI, плагины и ИИ.
4. `packages/platform-contracts/`: интерфейсы `LocalDb`, `VaultFs` (чтение/запись/наблюдение), `KeyStore`,
   `Notifications`. Только типы, без реализаций.
5. `packages/indexer/`: парсинг заметки в `{ title, headings, blocks (^id), links, embeds, tags, frontmatter,
   cardLinks (flippo://card/…) }`. Используй `@lezer/markdown` с теми же расширениями, что в редакторе (вынеси их
   в общий пакет `packages/markdown/`).
6. Инкрементальная индексация: индексатор получает события «файл изменён/удалён/переименован» и обновляет только
   затронутые записи. Хранение — через `LocalDb`.
7. Обратные ссылки: запрос «кто ссылается на заметку X» и «какие заметки прикреплены к карточке Y».
8. Тесты на наборе фикстур: небольшое хранилище в `packages/indexer/fixtures/` с краевыми случаями (ссылки на
   несуществующие заметки, `[[a|b]]`, ссылки на блоки, кириллица и пробелы в именах файлов, frontmatter с ошибкой).
9. Бенчмарк: полная индексация 5 000 заметок из P1 и инкрементальное обновление одной заметки. Запиши цифры.

## Готово, когда

- [ ] `domain` и `indexer` не зависят от React, Tauri и браузера (проверяется тем, что тесты идут в Node).
- [ ] Фикстуры покрывают синтаксис из 2.2 (уровни 1–2).
- [ ] Инкрементальное обновление одной заметки не переиндексирует всё хранилище.
- [ ] Ты можешь объяснить, чем команда отличается от события и почему домен не знает о базе.

## Ловушки

- Не храни «связь заметки с карточкой» в наборе — она живёт только в файле заметки и в личном индексе.
- Не смешивай путь файла и ID заметки: путь меняется при переименовании, ID — нет. Как хранить ID — решается на
  этапе 11; пока оставь это за интерфейсом.
